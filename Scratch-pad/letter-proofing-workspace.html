The Letter Proofing Workspace

The template editor was designed as a place to type. But nobody's real problem is typing — it's that a variable can render blank and no one finds out until a bank reads the letter. guestName is "blank when unknown." refundStatement is "empty when none." A blank leaves a ## Guest Contact History heading with nothing under it, in a document arguing for money. So: stop building an editor. Build a proofing bench.

01 — The turn

What changed in the thinking

The first pass restructured the modal: grouped the variable wall, gave the blast radius a caution band, added a meter. All true, all worth keeping — and all still in service of a screen whose central object is a textarea. That's the part that was wrong.

First pass

A better place to type

The template is the object. The operator writes {{contactSummary}}, sees a green pill, and has no idea whether that produces a paragraph or nothing at all.

"Affects 12 disputes" is a warning — a thing to feel bad about and click past. Validation only catches variables that don't exist, never ones that exist and come back empty.

This pass

A bench for proofing letters

The rendered letter is the object; the source is the tool that shapes it. You read the letter the way the bank will read it, against a real dispute, and page through the others.

"12 disputes" stops being a warning and becomes the proofing set. And every variable gets a coverage count — how many of those 12 it actually renders on — so a silent blank becomes a number you can see before you save.

1

Workspace chrome, not dialog chrome

Save and Close move to the top-right where a workspace keeps them, freeing the bottom edge for status. The title is just the template's name; a mono eyebrow carries what kind of thing it is. Compare with live sits next to Save because "what am I actually changing?" is a question you ask right before committing.

2

The blast radius becomes an instrument

The same fact the old paragraph buried — this hits 12 disputes — is now three readings: how many re-render, how many are insulated because someone edited them by hand, and how many come out with a sentence broken in half. That third number counts only the failures worth stopping for, not every honest empty section, and it is computed from the template you are editing.

A warning tells you to be careful. This tells you what to go look at, and gives you a way in.

3

The source is a tool, sized like one

Token highlighting, Markdown headings dropped to muted, function calls outlined. The Source / Split / Letter switch lives on this pane because it governs how much room the source gets — full width while you write, half while you check, gone while you proofread.

4

Proof against a real dispute, then the next one

Not sample data — an actual case from the 12 this template re-renders, with the arrows to page through them. Most template bugs are invisible on the happy-path record and obvious on the third one you check.

5

Values are marked as values

Interpolated text carries a faint accent tint, so you can see at a glance which sentences are authored and which came from the dispute. It's the rendered-side answer to token highlighting, and it makes a letter that's mostly data look different from one that's mostly argument.

6

The hole is drawn, not omitted

This is the whole point. A variable that renders empty shows as a hatched gap instead of silently closing up — and when a blank leaves an entire section with nothing under it, the section gets flagged bodily.

Page to dispute 3 and watch ## Guest Contact History become a heading with nothing beneath it, while the timeline reads - Mar 30, 2026 - booked and paid in full. That is what the bank would have received.

7

Coverage, graded by how the blank fails

Every variable in the template, ranked worst-first across the proofing set. But a raw fill count would cry wolf, because two variables can both be "empty on 9 of 12" and mean completely different things. The grade comes from where the token sits:

{{guestName}} sits mid-sentence, so an empty one ships - Jan 08, 2026 - booked and paid in full. to a bank. Broken prose — red, and worth stopping for. {{refundStatement}} stands alone on its line, so an empty one collapses its section instead, which the letter already flags bodily. Amber, and often correct: plenty of these disputes genuinely had no refund.

The useful part is that this is derived from the template, not from a hand-maintained list of which variables are allowed to be blank. Move a token into a sentence and its grade changes by itself. Clicking a row jumps the letter to a dispute where that variable is missing.

8

The palette, kept — but demoted

The grouped, filterable variable rail from the first pass survives intact; it was the right fix for the 27-chip wall. It just isn't the main event anymore, so it shares the rail with Coverage instead of occupying the bottom of the screen. Chips already used in the template carry the accent.

03 — Scope

What's re-layout, and what's new

You scoped the first pass form-only. This one isn't, and I'd rather say so plainly than bury it — the proofing idea needs behavior that doesn't exist yet. Everything in the first block is free; everything in the second is a real build, listed so you can cut it.

PieceKindWhat it needs
Workspace layout, header, status barform Markup and CSS in the existing modal shell. Same open/close path.
Token highlighting, grouped variable railform Carried over from the first pass. No logic change.
Source / Split / Letter switchform One piece of local state.
Rendered letter previewnew renderTemplate() already exists and is tested — this calls it against one dispute's vars and renders the Markdown. The cheapest new capability here.
Blank + empty-section markingnew Render with sentinel values instead of "", then mark them. Purely a render-time concern; the saved template is untouched.
Dispute pagernew The list of disputes this category template affects, plus their built vars. The panel knows the category; the query is the work.
Coveragenew Build vars for all N disputes, count non-empty per variable. Needs the same query as the pager, so they ship together or not at all.
Blank severity gradingfree Derived from the template by checking whether a token shares its line with prose. No catalog flag, no new field, nothing to keep in sync — about fifteen lines.
Compare with livenew A diff of editor text against the saved template. Nice, not load-bearing — cut first if something has to go.

If you want only the free half, it degrades honestly: the workspace layout, the switch, and the rail all stand on their own, and the letter pane becomes a preview against the single dispute already open in the panel — still better than editing blind, without the query work.

Built on the app's own system — Instrument Serif, Inter Tight, JetBrains Mono, the Taupe-Grey ramp, the green accent, --amber-* for caution, --pos/--neg for coverage severity. No new color tokens. The twelve disputes are fixtures drawn from lib/fixtures.ts's real reason codes, providers, and merchants; coverage is computed from them at runtime, so nothing in the rail is a drawing.

One finding worth passing on, from measuring this page: the shipped primary button pair — --accent-fg white on --accent green — measures 2.41:1, well under the 4.5 floor for its 13px label, in both themes. The Save button above is left exactly as the app renders it rather than quietly corrected inside one mockup, because it is an app-wide token pair and not a template-editor decision. Dropping --accent to roughly oklch(0.52 0.16 145) for button surfaces clears it without moving the hue. Everything else on this page measures above 4.5 in both themes.
